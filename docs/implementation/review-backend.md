- Blocker (High): Encryption key validation is too weak for a safety-critical secret store. `APP_ENCRYPTION_KEY` silently defaults to a known development string (`backend/src/config/env.ts:35`), and `getKey()` accepts any non-32-byte or invalid-base64 value by hashing it into a 32-byte key (`backend/src/utils/crypto.ts:11-16`). Production only rejects keys containing `dev-only` (`backend/src/config/env.ts:44-46`), so `APP_ENCRYPTION_KEY=password` would be accepted and used to encrypt broker/API credentials. Sprint 1 explicitly requires an encryption utility backed by `APP_ENCRYPTION_KEY` (`docs/implementation-plan.md:109-112`), and API keys must be encrypted at rest (`docs/implementation-plan.md:712`); this should fail fast unless the configured key decodes to exactly 32 bytes (or otherwise meets a documented strong format) and should not have a usable default outside tests.

- Blocker (High): Trading risk settings accept unsafe numeric values without validation. `PUT /settings/trading` coerces inputs with `Number(...)` and persists them directly (`backend/src/routes/settings.ts:57-69`), allowing negative values, `NaN`, `Infinity`, decimals for integer columns, or absurdly large values. These fields are the foundation for later risk limits (`maxDailyLoss`, `maxTradesPerDay`, `maxCapitalPerTrade`, `maxOpenPositions`) in `backend/src/db/schema.ts:42-52`; accepting invalid/negative limits can corrupt the risk-control foundation before execution features are built. Validate finite non-negative integers with sensible bounds before persistence and return 400 on invalid input.

- Blocker (High): API-key upsert is not protected by a database uniqueness constraint or atomic conflict handling. The schema has no unique constraint for `(user_id, provider, label)` (`backend/src/db/schema.ts:20-31`), while `upsertApiKey()` does a read-then-insert/update sequence (`backend/src/routes/settings.ts:23-36`). Concurrent settings updates can insert duplicate active secrets for the same provider/label, making credential selection ambiguous and undermining the “duplicate prevention” safety posture expected before execution (`docs/implementation-plan.md:711`). Add a unique index/constraint and use `onConflictDoUpdate` on that constraint.

- Blocker (Medium): Malformed login requests can become 500 responses instead of authentication/client errors. `/auth/login` calls `normalizeCredentials(body)` outside a try/catch (`backend/src/routes/auth.ts:63-64`); `normalizeCredentials()` throws for invalid email/password (`backend/src/routes/auth.ts:12-18`), and the global error handler maps non-404 errors to 500 while returning the exception message (`backend/src/index.ts:13-17`). This is both correctness and information-disclosure risk for the auth boundary. Handle validation failures explicitly with 400, as registration currently does (`backend/src/routes/auth.ts:46-61`).

- Note (Medium): API-key lifecycle auditing is incomplete versus Sprint 1. The plan requires audit logs for “API key create/update/delete” (`docs/implementation-plan.md:124-129`), but provider updates only emit one aggregate `settings.providers.update` audit event (`backend/src/routes/settings.ts:78-95`), and there is no delete/clear path for stored keys (`upsertApiKey()` ignores empty strings at `backend/src/routes/settings.ts:23-24`). This leaves credential create vs update vs deletion untraceable and makes credential removal impossible through the current API.

- Note (Medium): Registration is not transactional. `/auth/register` inserts the user, settings, preferences, audit log, and session in separate statements (`backend/src/routes/auth.ts:49-55`). If any later insert fails after the user row is created, the catch returns 400 (`backend/src/routes/auth.ts:58-60`) but may leave a partially initialized account. Wrap registration setup in a database transaction so auth/session/settings foundation state is all-or-nothing.

- Note (Medium): Cookie-authenticated state-changing endpoints do not include a CSRF defense beyond `SameSite: 'lax'`. Session cookies are HTTP-only and same-site lax (`backend/src/routes/auth.ts:25-33`), and settings/logout mutate state based solely on that cookie (`backend/src/routes/settings.ts:53-112`; `backend/src/routes/auth.ts:75-81`). Before adding broker credentials and trading controls, add an explicit CSRF token or equivalent protection for cookie-authenticated mutation routes.
